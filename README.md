# AeroQ — Aerospace Manufacturing Quality Data Pipeline

An end-to-end data engineering project that turns messy, disconnected shop-floor data into a governed quality warehouse, automated data-quality gates, anomaly alerts, a query API, and a stakeholder dashboard.

It's built around a realistic scenario: an aircraft production line where **MES work orders**, **quality inspections/nonconformances**, and **autoclave sensor readings** live in three separate systems, in three formats, with the usual real-world problems (duplicates, inconsistent codes, orphan records, sensor glitches, and PII).

![AeroQ dashboard](https://raw.githubusercontent.com/Delicatessen0/Portfolio-General/main/images/aeroq_quality_pipeline.jpg)

*Live dashboard: [projects/aeroq/dashboard.html](https://delicatessen0-general.surge.sh/projects/aeroq/dashboard.html) · also generated locally at `reports/dashboard.html` on every run.*

> All data is synthetic and generated by `src/aeroq/generate.py`. No real program, part, or personnel data is used.

## What it does

| Stage | What happens | Tech |
|---|---|---|
| **Extract** | Pulls from 3 source systems: MES work orders (CSV), QMS inspections (JSON), autoclave historian (CSV), plus the part master | pandas |
| **Transform** | De-duplicates, conforms codes and casing, derives cycle time and first-pass flags, quarantines orphans and out-of-range sensor values instead of dropping them, masks inspector PII | pandas |
| **Model** | Star schema: `dim_part`, `dim_work_center`, `dim_date` → `fact_work_order`, `fact_inspection`, `fact_sensor_reading` | SQLAlchemy 2.0 ORM |
| **Data quality** | Declarative rule suites (not-null, unique, FK, range, set, custom expressions) with `error` / `warn` severity. Results go to `dq_result`, and any error-level failure stops the load | Custom framework |
| **Load** | Idempotent, transactional full refresh in batches. The same code targets SQLite, SQL Server, Azure SQL, or Oracle by changing `AEROQ_DB_URL` | SQLAlchemy |
| **Analytics** | Reusable library: first-pass yield, defect Pareto, weekly defect rate, Cp/Cpk, cycle time, disposition mix | SQL + pandas |
| **Anomaly detection** | SPC p-charts per work center plus Isolation Forest on multivariate cure profiles | NumPy, scikit-learn |
| **Serve** | FastAPI with role-based column filtering (`engineer` / `analyst` / `external`) and OpenAPI docs | FastAPI |
| **Visualize** | Self-contained HTML dashboard plus CSV extracts ready for Tableau or Power BI | Chart.js |
| **Orchestrate** | Built-in DAG runner for local use, plus Dagster assets with a blocking DQ asset check and a daily 5 AM PT schedule | Dagster |
| **CI** | GitHub Actions runs the tests and the full pipeline, then uploads the dashboard as a build artifact | pytest |

## Findings from the sample run

The generator includes a hidden process drift: an autoclave thermocouple slowly degrades starting around week 22. The pipeline finds it without being told where to look:

- **The SPC p-chart flags Autoclave Cure as out of control in 10 weeks between W23 and W40.** The only other signal is a single week at 5-Axis CNC, the kind of isolated false alarm you expect when watching six charts at 3σ.
- **First-pass yield for Autoclave Cure drops to 74.5%,** compared with 85–88% for every other work center.
- **Isolation Forest separates two groups of cure profiles.** The later, hotter group has rising temperature slopes, and the model flags the most extreme individual builds for engineering review.
- **Cpk is about 0.85 on all measured characteristics,** well below the usual aerospace target of 1.33. The process is not yet capable.
- **Data-quality warnings show real issues in the source data:** 91 work orders marked CLOSED with no close date, and 12 orphan inspections referencing work orders that don't exist (quarantined, not loaded).

## Architecture

```
 MES (CSV) ─┐
 QMS (JSON) ┼─► extract ─► transform ─► DQ gate ─► load ─► SQL warehouse (star schema)
 Historian ─┘     │           │  └─► quarantine        │
                  │           └─► PII masking           ├─► analytics library ─► FastAPI
                  │                                     ├─► anomaly detection (SPC + IsolationForest)
                  └──────── Dagster asset lineage ──────┴─► dashboard.html + Tableau/Power BI extracts
```

## Quick start

```bash
git clone <this repo> && cd aero-quality-pipeline
python -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"

aeroq                        # run the full pipeline → reports/dashboard.html
pytest -q                    # 10 tests: ETL, DQ gate, PII, SPC detection, API roles
uvicorn aeroq.api:app        # API docs at http://localhost:8000/docs
```

Run it with Dagster:

```bash
pip install -e ".[dagster]"
dagster dev -f orchestration/dagster_defs.py
```

Point it at SQL Server instead of SQLite:

```bash
pip install -e ".[sqlserver]"
export AEROQ_DB_URL="mssql+pyodbc://user:pass@host/aeroq?driver=ODBC+Driver+18+for+SQL+Server"
aeroq
```

## Data governance

- **Classification:** every sensitive column is tagged (`PII-MASKED`, `CUI`, `INTERNAL`) in `governance.py`.
- **PII:** inspector names are replaced with a salted SHA-256 hash before they reach the warehouse. Analysts can still group by inspector, but no names are stored.
- **Least privilege:** the API removes columns based on the caller's role. In production the role would come from Entra ID / Azure AD claims.
- **Auditability:** every pipeline run writes its DQ results with a `run_id`, so data-quality trends can be queried over time (see `sql/analyst_queries.sql`).
